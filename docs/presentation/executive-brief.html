Feature flags at KTO

Our own feature flag platform, without licence costs

ktoggle is a feature flag and experimentation service built in-house, compatible with the GrowthBook SDKs we already use. It covers the flag and rollout capabilities we use today, includes the governance features GrowthBook only sells in its Enterprise plan, and adds an audit layer GrowthBook does not have: every decision can be proven and replayed.

What it is
A drop-in replacement for GrowthBook's flag delivery. Existing GrowthBook SDKs connect by changing the host and the client key.
Cost model
No per-seat licence. We pay for infrastructure (a few small AWS resources) and the team time to own it.
What we gain
Signed, immutable bundles: we can prove what any service received and replay any past decision.
What we give up
GrowthBook's statistics engine and visual editor. Experiment analysis stays in Mixpanel.
01

What ktoggle is

GrowthBook today does two jobs for us: it holds the flag configuration (who sees what) and it delivers that configuration to our services, which evaluate flags locally with the GrowthBook SDKs. ktoggle takes over both jobs while keeping the SDKs unchanged.

Internally it has its own domain model (features, environments, rules, saved groups, projects, SDK connections). At the edge it emits exactly the payload the GrowthBook SDKs expect, on the same endpoints (/api/features/{clientKey} and the streaming endpoint /sub/{clientKey}). For a service, migrating would mean changing two configuration values, not code.

Who uses it and how

  • Product and engineering use the console, which mirrors GrowthBook's layout so the learning curve is close to zero.
  • Services and apps keep the official GrowthBook SDKs (Java, Node, React, and any other language GrowthBook supports).
  • Security, compliance and auditors get a hash-chained audit trail, signed bundles and decision replay.
  • Sign-in goes through Keycloak (OIDC), with roles viewer, editor, approver and admin.

Technology

Java 21 and Spring Boot 3.5 (virtual threads), PostgreSQL, Redis, AWS KMS and S3. The console is React and TypeScript. The stack follows the house standard used in our newest services, so any squad can maintain it.

02

How a change reaches production

Every change starts as a draft. Nothing reaches an SDK until the draft is published, and environments that require review (production, by default) need someone else's approval first.

Draft

Edit rules, values or prerequisites. Side-by-side diff against what is live.

Review

Four-eyes approval where required. Configurable approvers; self-approval off by default.

Publish

New revision plus an audit entry with author, reason and change id.

Seal

Payload compiled per SDK connection, hashed (RFC 8785 + SHA-256), signed with KMS.

Activate

Appended to a hash-chained activation log; copy archived to S3 with Object Lock.

Deliver

Redis tells every pod; pods verify the signature and push the payload over SSE.

How fast services see it

On the server side, publishing is immediate: under a second from "Publish" to every pod serving the new payload. How fast an application sees it depends on how its SDK is configured. That works the same way with GrowthBook today.

SDK modeUsed byTime to see a change
Streaming (SSE)Web and app SDKs with streaming on; Java SDK with SERVER_SENT_EVENTS~1 s
Polling with cache TTLOur Java services today (stale-while-revalidate)Up to the TTL, ~30 s today, same as GrowthBook

Polling is also cheaper than with GrowthBook: ktoggle answers with the bundle hash as an ETag, so an unchanged configuration costs a 304 Not Modified with no body.

When something fails

  • ktoggle is unreachable: SDKs keep evaluating with the last payload they received, so flags keep working with the last known configuration.
  • A pod misses a publication: a reconciler republishes every minute; publication is idempotent.
  • Someone tampers with a stored bundle: pods verify hash and signature before serving, refuse the forged bundle, keep serving the last valid one, and the chain verification points to the broken link.
  • Scheduled rules are switched on and off within about 10 seconds, and each switch is recorded as done by system:scheduler.
03

What GrowthBook does not have: provable decisions

This is the main differentiator. It applies the principle of our internal veredict engine: every decision must be auditable reliably and independently of the software version. GrowthBook keeps an audit log of who changed what, but it cannot show exactly what a given service was evaluating at a given moment, or reproduce a past decision.

  • Immutable, signed bundles. Each published configuration is a content-addressed bundle (canonical JSON, SHA-256), signed with an AWS KMS key. Database triggers reject any update or delete, and a copy goes to S3 with Object Lock (WORM).
  • Hash-chained history. Bundle activations and the audit log are chained like a ledger. Any edit made directly in the database breaks the chain, and the console shows where.
  • Replay. "What did user X get on 14 March at 10:42?" The answer comes from re-running the official GrowthBook SDK against the bundle that was active at that instant, not from guessing.
  • Delivery log. Which client key received which bundle, and when. It answers "did the Android app already have the fix at 14:03?" without storing IP addresses.
  • Decision log (opt-in), LGPD-safe. Services can report decisions. Personal attributes are never stored in clear: only an HMAC digest, which can later confirm "these are the attributes that produced this decision" without keeping the data.
  • Rollback with a reason. Re-activating a previous bundle is one action. It pins the connection until someone unpins it, and it is audited like any change.

For a regulated betting operator this turns "we believe the bonus was off for that player" into evidence a regulator or a dispute process can verify.

Cost: licences versus infrastructure

GrowthBook charges per seat, caps users and projects on its self-serve plans, and bills CDN traffic above the plan allowance. The features we rely on for governance are only in Enterprise, priced by quote. ktoggle has no licence. Its running cost is a handful of small AWS resources, most of which fit into what we already operate.

  • CDN: 2M requests and 20 GB per month included, then US$ 10 per million requests and US$ 1 per GB.
  • No approvals, scheduled flags, prerequisites, audit log, SSO/SCIM or encrypted endpoints.

The real comparison is our GrowthBook contract against infrastructure plus the time of the team that owns ktoggle (maintenance, upgrades, on-call). That team time is the main cost of building in-house and should be budgeted explicitly.

Beyond the invoice

  • No seat limit: everyone who needs to see or approve flags can have access, including compliance, support and product.
  • Data stays in our AWS account (sa-east-1). Flag configuration and decision data never leave the company, which simplifies LGPD.
  • No vendor lock-in on delivery: the SDKs are GrowthBook's open-source (MIT) libraries, so we keep compatibility without depending on GrowthBook's service.

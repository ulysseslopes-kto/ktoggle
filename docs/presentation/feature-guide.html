Feature guide · October 2026

Everything ktoggle does, explained

ktoggle is KTO's feature flag and experimentation service, compatible with the GrowthBook SDKs our apps already use. This guide walks through every feature: what it does, how it works, and what to know about it. No code needed to follow it.

01

Flags and targeting

The building blocks: what a flag is, where it applies and who gets which value.

Features (flags)

GrowthBook: all plans

A feature is a named switch or setting that applications read at runtime, so behaviour can change without a deploy.

How it works

  • Each feature has a key (for example new-checkout), a type (on/off, text, number or JSON) and a default value.
  • Rules on top of the default decide who gets something else. They are evaluated top to bottom; the first one that applies wins.
  • Description, owner and tags help find and own features. The list shows the most recently changed first.
  • Features are never deleted, only archived, because past bundles and audits refer to them.

Good to know

  • The value type is fixed at creation and validated on every change: a number flag can never be served text.
  • JSON flags carry structured configuration, such as a bonus with percent, cap and rollover.
In the console: Features.

Environments

GrowthBook: all plans

The same feature can be on in staging and off in production, with different rules in each.

How it works

  • Each feature has, per environment, an on/off switch and its own list of rules.
  • When a feature is off in an environment, apps there do not receive it at all and evaluate it as off.
  • An environment can be marked requires review: changes that reach it need an approval (see Review and approval).

Good to know

  • In the demo, Production requires review and Staging does not.
In the console: Configuration → Environments; feature page tabs.

Projects

GrowthBook: 1 (free), 3 (Pro), more on Enterprise

Group features by product area (payments, casino, sportsbook) and limit what each app receives.

How it works

  • A feature belongs to at most one project.
  • An SDK connection can be limited to some projects, so an app downloads only the flags it needs.
  • Projects can also limit who edits their features (see Per-project permissions).

Good to know

  • No limit on the number of projects.
In the console: Configuration → Projects.

Attributes

GrowthBook: all plans

The catalog of user properties rules can target: country, app version, VIP level, user id and so on.

How it works

  • Each attribute has a type (text, number, boolean, lists, or a fixed set of values).
  • Rules may only reference attributes from the catalog, so typos are caught before they ship.
  • One or more attributes are marked as hash attributes (usually the user id): they make rollouts and experiments sticky per user.
  • Attributes can be flagged as personal data; the decision log then never stores them in clear (LGPD).

Good to know

  • Apps send attributes to the SDK, which evaluates locally: user data does not leave the app (except with remote evaluation, by choice).
In the console: Feature flags → Attributes.

Targeting conditions

GrowthBook: all plans

Describe who a rule applies to, from simple ("country is BR") to complex (app version at least 2.3 and VIP level 3 or more).

How it works

  • A visual builder (attribute, operator, value) covers everyday cases; a JSON mode accepts the full GrowthBook condition language.
  • Supported operators include equals, in list, greater than, regex, exists, version comparisons and and/or/not combinations.
  • Every condition is validated against the attribute catalog before it can be saved.

Good to know

  • Rules read in plain words on the feature page, for example "IF country equals BR AND in group VIPs".

Saved groups (all, any, none)

GrowthBook: all plans

Reusable audiences, such as "beta testers" or "VIPs", that many rules can target and that change in one place.

How it works

  • A group is either a list of values for one attribute (for example, user ids) or a condition (for example, VIP level 3 or more).
  • In a rule, each group is required (must be in), part of an any of set (at least one), or excluded (must not be in).
  • Changing a group updates every rule that uses it at the next publication.

Good to know

  • A group used by any rule cannot be deleted.
  • A rule cannot both require and exclude the same group.
In the console: Feature flags → Saved groups; rule editor.

Force rules

GrowthBook: all plans

Give a specific value to everyone who matches the rule.

How it works

  • Condition and/or saved groups decide who matches; matching users get the rule's value.
  • Typical uses: turn something on for testers, one country, or a VIP tier.

Good to know

  • Any rule can also be scheduled and depend on other features (see below).

Percentage rollouts

GrowthBook: all plans

Release to a share of users (5%, 25%, 100%) and grow it gradually, with the same users staying in as it grows.

How it works

  • Each user's hash attribute (the user id) is turned into a stable number between 0 and 1.
  • Users whose number falls under the percentage get the value. Raising 25% to 50% keeps the first 25% and adds more.
  • The calculation is identical in every app, server and language, so a user sees the same thing everywhere.

Good to know

  • Rollouts imported from GrowthBook keep GrowthBook's seed, so no user moves in or out of a rollout because of the migration.

A/B experiments

GrowthBook: all plans (statistics engine not in ktoggle)

Split users between two or more variations and send each exposure to analytics (Mixpanel) to measure which one wins.

How it works

  • An experiment has a tracking key, variations with values and weights (for example 34/33/33), the share of users included and the hash attribute.
  • The SDK assigns each user a variation deterministically: the same user always gets the same variation, in any replica or app.
  • When a user sees an experiment, the SDK calls the app's tracking callback with the experiment and the variation; that is what goes to Mixpanel.
  • "Test feature" and "Replay" show which variation a user got and whether they were in the experiment.

Good to know

  • Raising the share of users only adds people; changing weights reshuffles some of them, so treat it as a new phase.
  • Results analysis stays in Mixpanel or the warehouse: ktoggle has no statistics engine.
In the console: rule editor → Experiment. Demo: deposit-button-copy.

Scheduled rules

GrowthBook: Enterprise

Turn a rule on and off at set times, for example a Black Friday bonus from Friday to Monday, without anyone at the keyboard.

How it works

  • Any rule can have a start, an end, or both (in the editor's time zone).
  • Outside its window the rule is simply not sent to apps. ktoggle publishes a new configuration within about 10 seconds of each start and end.
  • Each switch is recorded as done by system:scheduler, with the rule that changed.

Good to know

  • The rule list shows Scheduled, Live or Ended.
  • "Evaluate at" in Test feature previews what a user will get at a future date.
Demo: welcome-bonus → Production → "Black Friday boost".

Prerequisites

GrowthBook: Enterprise

Make a feature depend on another: "instant cashback" only for users who already have the new checkout.

How it works

  • On a feature: unless every parent condition passes for the user, the feature is off for them, in every environment.
  • On a rule: if the parent fails, only that rule is skipped and evaluation continues.
  • Conditions: parent is on, off, live, not live, equals a value, or a custom condition.
  • The parent's page lists the features that depend on it.

Good to know

  • Cycles (a needs b, b needs a, through any chain) are rejected, and parents must be in the same project.
  • Changing prerequisites needs approval in protected environments, like the default value.
Demo: instant-cashback depends on new-checkout.

Test feature

GrowthBook: all plans

Check what a given user gets before (and after) publishing, using the same SDK that runs in production.

How it works

  • Pick an environment, type the user's attributes and evaluate. The panel shows the value, which rule produced it and why each rule did or did not apply.
  • While a draft is open, it evaluates the draft, so you see the effect before publishing.
  • "Evaluate at" simulates a future date, for scheduled rules.

Good to know

  • It also explains experiments (variation, bucket) and prerequisite gates.
02

Changing flags safely

Who can change what, how changes are reviewed, and how every change is traced back to a person and a reason.

Drafts and diff

GrowthBook: Enterprise

Every change starts as a draft. Nothing reaches an app until the draft is published.

How it works

  • The first edit on a feature opens a draft automatically. Several edits can be grouped in one draft.
  • "Review & publish" shows a side-by-side diff: what is live now and what it will be after publishing.
  • If someone publishes another change meanwhile, the draft is merged section by section; real conflicts are shown and must be resolved explicitly.

Good to know

  • Toggling a flag from the list also goes through a draft.

Review and approval (four eyes)

GrowthBook: Enterprise

Changes to protected environments, such as production, need someone else's approval.

How it works

  • The author requests a review with a comment; reviewers find it on the Reviews page (with a pending counter).
  • Reviewers approve or request changes. Changing an approved draft resets the approval (configurable).
  • Admins configure who can approve (Keycloak roles and/or users) and whether authors may approve their own drafts (off by default).

Good to know

  • Changes that affect every environment (default value, prerequisites, archiving) need approval if any protected environment is affected.
  • Automation (API tokens) can never approve: reviews are always made by people.
In the console: Reviews; Configuration → Settings.

Emergency publication

GrowthBook: Enterprise

In an incident, an admin can publish without waiting for approval, with a mandatory reason.

How it works

  • Allowed only to admins, and only if enabled in Settings.
  • The reason is mandatory and is stored in the audit trail. The event is marked "published WITHOUT APPROVAL".
  • A webhook can notify a channel every time it happens.

Good to know

  • Speed for incidents without losing traceability.

Revisions and revert

GrowthBook: all plans

Every publication creates a numbered revision; any past revision can be restored.

How it works

  • The revision history shows who changed what, when and why.
  • "Revert" opens a draft with the old content, which goes through the same review as any change.

Good to know

  • History is never rewritten: a revert is a new revision.

Sign-in and roles

GrowthBook SSO/SCIM: Enterprise

Single sign-on through Keycloak (the company identity provider) with four roles.

How it works

  • Viewer reads everything, tests and replays.
  • Editor also creates and edits drafts.
  • Approver reviews drafts when listed in the review settings.
  • Admin also manages environments, connections, settings, tokens and webhooks.

Good to know

  • No per-seat cost: everyone who needs access can have it.

Per-project permissions

GrowthBook custom roles: Enterprise

Limit who can change a project's features: only the payments squad edits payments flags.

How it works

  • Each project can list the Keycloak roles and users (or API tokens) allowed to change its features. With no list, every editor can.
  • Blocks creating features, editing drafts, requesting review and publishing. Moving a feature between projects needs rights on both.
  • Outsiders see the feature read-only, with an explanation.

Good to know

  • Reading, testing and reviewing stay open. Admins always have access.

API tokens

GrowthBook: available

Credentials for automation (CI pipelines, scripts) to read or edit flags without a person signing in.

How it works

  • Admins create a token with a role (viewer or editor) and an expiry (30 days, 90 days, a year or never).
  • The secret is shown once; ktoggle stores only its hash. Revoking cuts access immediately.
  • Everything done with a token is audited as token:<name>; last use is recorded.

Good to know

  • Tokens can never be admins, approve drafts or manage other tokens.
In the console: Configuration → API tokens.

Webhooks and notifications

GrowthBook: available

Tell Slack, or any system, when reviews are requested, drafts approved, changes published, rollbacks made or schedules switch.

How it works

  • Each webhook picks its events and a format: a ready-made Slack message or signed JSON.
  • Notifications are saved together with the change they announce, then delivered by any server, with retries (30 s up to 8 min).
  • Every request is signed (HMAC-SHA256), so receivers can verify it came from ktoggle.
  • The console shows recent deliveries, attempts and responses, and has a "Send test" button.

Good to know

  • If the change is saved, its notification exists; if not, nothing is sent.
In the console: Configuration → Webhooks.
03

Delivering flags to applications

How a published change reaches apps and services, how fast, and what happens when something fails.

SDK connections and GrowthBook compatibility

GrowthBook: all plans

Each app reads its flags with a client key, through the official GrowthBook SDKs, unchanged.

How it works

  • A connection ties a client key to an environment and, optionally, some projects.
  • ktoggle serves the same endpoints and format as GrowthBook (/api/features/{key}, /sub/{key}), so migrating an app means changing the host only.
  • Every build checks compatibility against the official Java SDK, and the end-to-end tests against the JavaScript SDK.

Good to know

  • The connection page has ready-to-use snippets for Java, JavaScript and React.

Streaming and polling

GrowthBook: all plans

A published change reaches every server immediately; apps see it in about a second when streaming.

How it works

Publish→Seal bundle→Notify all servers→Push to apps
SDK modeTime to see a change
Streaming (SSE)~1 s
Polling with cacheUp to the cache time (~30 s in our Java services today, same as GrowthBook)

Good to know

  • Polling is cheap: if nothing changed, the answer is "not modified", with no body.
  • Each environment is independent: a staging change never touches production payloads.

Many servers and failures

ktoggle

ktoggle runs on several servers at once and keeps flags working when parts fail.

How it works

  • Every server keeps the active configuration in memory; requests from apps never touch the database.
  • Redis tells all servers about a new publication; a reconciler republishes anything missed every minute.
  • Apps keep evaluating with the last configuration they received, so a ktoggle outage freezes flags instead of breaking apps.

Good to know

  • A tampered configuration is refused and the server keeps serving the last valid one.

Encrypted payloads

GrowthBook: Enterprise

Hide rules and values from anyone inspecting browser or app traffic.

How it works

  • Per connection, the payload is sent encrypted (AES), in GrowthBook's exact format; the SDK decrypts it with the connection's key.
  • Admins reveal and rotate the key; turning it on, off or rotating takes effect on every server without a new configuration.

Good to know

  • The key ships inside apps: this stops casual inspection, not a determined attacker.
  • The audit copy stays in clear text, so replay and verification are unaffected.

Remote evaluation

GrowthBook: Pro

The app sends the user's attributes and gets only the values; no rule ever reaches the browser.

How it works

  • Per connection; the SDK switches to remote mode with one option.
  • ktoggle evaluates with the official SDK against the active, verified configuration; every answer carries its bundle hash.
  • Experiments still fire the tracking callback, without revealing weights or coverage.

Good to know

  • Meant for browsers and apps; backend services usually keep local evaluation (faster, works offline).
  • Cannot be combined with encryption (it would be redundant), as in GrowthBook.

SDK playground

ktoggle

A live SDK inside the console, to watch a change arrive and see what a user gets.

How it works

  • Connects the official JavaScript SDK to any connection, including encrypted and remote-evaluation ones.
  • Shows every feature's value for the given attributes, flashes what changes and logs experiment exposures.

Good to know

  • The quickest way to show a change going live during a demo.
04

Proving every decision

What GrowthBook does not have: evidence of exactly what each app received and what each user got, at any point in time.

Signed, immutable bundles

ktoggle only

Every configuration served to apps is sealed: fingerprinted, signed and stored where it cannot be altered.

How it works

  • Each publication produces a bundle per connection: the exact payload, which feature revisions it came from and which evaluator reads it.
  • The bundle gets a fingerprint (canonical JSON, SHA-256) and a digital signature (AWS KMS).
  • The database refuses any edit or deletion, and a copy goes to S3 with Object Lock (write once, read many).
  • Servers verify fingerprint and signature before serving a bundle.

Good to know

  • Republishing identical content produces the same fingerprint: no noise in the history.

Activation chain and integrity check

ktoggle only

The sequence of configurations each connection served is linked like a ledger: any tampering shows.

How it works

  • Each activation (publish, rollback, schedule switch) records who, when, why and a link to the previous one.
  • "Verify" recomputes the chain and points to the exact entry that was altered, if any.

Good to know

  • Shown on each SDK connection page, with the active bundle's verified signature.

Rollback

ktoggle only

Put a connection back on a previous configuration in one action, with a reason.

How it works

  • Pick any earlier bundle of the connection; it becomes active immediately on every server.
  • The connection is pinned: new publications wait until someone unpins it, so the incident fix is not overwritten.

Good to know

  • Audited, and can notify a channel through webhooks.

Replay

ktoggle only

Answer "what did this user get on 14 March at 10:42?" with evidence, not guesses.

How it works

  • Replay by bundle, or by connection and instant (ktoggle finds the bundle active at that moment).
  • The decision is recomputed with the official SDK on that exact bundle: value, rule, experiment variation and why.
  • The answer stays the same even if the configuration changed many times since.

Good to know

  • Useful for player disputes, regulator questions and incident analysis.
In the console: Auditing → Replay.

Delivery log

ktoggle only

Which app received which configuration, and when.

How it works

  • Per client key and hour: which bundle was delivered, how many times, through polling, streaming or remote evaluation.
  • Answers "did the Android app already have the fix at 14:03?".

Good to know

  • No IP addresses are stored; only the SDK name from the user agent.

Decision log (LGPD-safe)

ktoggle only

Optionally, apps report the decisions they made, so they can be audited later.

How it works

  • Each event records the bundle, feature, value and rule, plus the user's non-personal attributes.
  • Personal attributes are never stored in clear: only a keyed fingerprint (HMAC), which can later confirm "these attributes produced this decision".

Good to know

  • Opt-in per app; stored in monthly partitions with configurable retention.

Audit log

GrowthBook: Enterprise (exportable, not tamper-evident)

Every change to anything (flags, groups, environments, tokens, webhooks) with who, what, when and why.

How it works

  • Before and after of every change, the person or token, the reason and a change id linking it to revisions and bundles.
  • Entries are chained, so any edit made directly in the database breaks the chain and is detected.

Good to know

  • Secrets (tokens, webhook and encryption keys) never appear; only fingerprints.
In the console: Auditing → Audit log.
05

Migrating from GrowthBook

Built and tested on our side, ready to use once the move is approved. Read-only towards GrowthBook.

Importer

ktoggle

Brings GrowthBook's configuration into ktoggle, keeping every user's values and variations.

How it works

  • Reads projects, environments, attributes, saved groups, features and SDK connections from GrowthBook's API.
  • Dry run first, with a report per item: create, update, unchanged, unsupported, failed.
  • Keeps client keys, rule ids, rollout seeds, experiment hashing and encryption keys.
  • Idempotent: running it again applies only what changed in GrowthBook.

Good to know

  • What has no equivalent (safe rollouts, namespaces, bandits, visual editor) is reported, never dropped silently.
  • Environments can be mapped, for example production → prd.

Shadow mode

ktoggle

Proves, connection by connection, that ktoggle serves exactly what GrowthBook serves, before anyone switches.

How it works

  • For each client key, both payloads are evaluated with the official SDK for the same 2,000 simulated users, built from the values the rules compare with.
  • Any feature where a user would get a different value is reported, with examples (user, GrowthBook value, ktoggle value).
  • After 3 clean runs in a row, the connection is marked ready to migrate. Metrics allow alerting.

Good to know

  • Validated against a real (local) GrowthBook: a 25%→30% rollout change was caught (11 of 2,000 users), and a re-import brought it back to a match.
  • Never uses real user data.
In the console: Migration → From GrowthBook.

Cutover runbook

ktoggle

A step-by-step plan to move each service, with a rollback that is one configuration change.

How it works

  • Needed after approval: a read-only GrowthBook key, network access, the environment mapping.
  • Import, run shadow mode until ready, freeze the service's flags in GrowthBook, switch the host in its deployment values.
  • Rollback: revert the host. GrowthBook still holds the configuration.

Good to know

  • One service at a time, least critical first; payments and bet placement last.
06

Under the hood

How it is built, how it is tested and how it is run.

Architecture

ktoggle

A standard house stack any squad can maintain.

How it works

  • Backend: Java 21, Spring Boot 3.5 (virtual threads), PostgreSQL, Redis, AWS KMS and S3.
  • Console: React 19 and TypeScript, Tailwind, TanStack Query, Radix, Keycloak sign-in.
  • Feature-oriented packages with enforced layering: architecture tests fail the build on dependency cycles.

Good to know

  • No vendor lock-in: the SDKs are GrowthBook's open-source libraries.

Quality and tests

ktoggle

Every feature is covered at several levels, including against the real SDKs.

How it works

LevelCountCovers
Unit316Rules, validation, merging, permissions, crypto, sampling
Integration55Full API on a real PostgreSQL, security, audit chains
SDK contract16+Payloads evaluated by the official Java SDK, including GrowthBook's own output
End to end19The console in a real browser, sign-in, drafts, JS SDK live

Good to know

  • Several real bugs were caught by these tests before anyone saw them: an editor token listing tokens, a review gap on prerequisites, a hash seed that would have moved users.

Operations

ktoggle

Observable, cheap to run and easy to try.

How it works

  • JSON logs and Prometheus metrics: publication time, streaming connections, bundle integrity failures, webhook deliveries, shadow divergences.
  • Health checks and graceful behaviour when Redis or the database are briefly unavailable.
  • The whole product runs locally with one command, with demo data, users per role and an optional local GrowthBook.

Good to know

  • Running cost is infrastructure only: no licence, no per-seat price.
